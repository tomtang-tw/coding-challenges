## Detailed Category Feedback

### Core Logic Analysis

The `FindNextValidMember()` method is a clean, correct implementation of round-robin with inactive skipping. The algorithm: (1) filter active members, (2) handle zero-active and single-active edge cases with early returns, (3) find last selected index, (4) search circularly using `(lastIndex + i) % _members.Count`, (5) return first active candidate that isn't the last selected.

The use of `int? _lastSelectedId` (nullable) is elegant — when null, `FindIndex` returns -1, and `(-1 + 1) % count = 0` naturally starts from the first member. This eliminates the need for a separate "first call" flag or initialization logic.

The `GetNext(count)` method correctly calls `FindNextValidMember()` in a loop, updating `_lastSelectedId` after each selection. This means batch requests (e.g., `GetNext(3)`) maintain proper rotation state, and subsequent calls continue from the correct position.

### Code Quality Analysis

This is the most concise and clean codebase reviewed. The C# idioms are exemplary: `readonly List<Member>` for immutable collection reference, `int?` nullable value type for optional state, LINQ for filtering (`Where`, `Any`, `First`), and standard .NET exception (`InvalidOperationException`) for invalid state.

The `Member` class demonstrates proper immutability — all properties are get-only, constructed once via constructor. This prevents the class of bugs where member state is accidentally modified during rotation.

The main gap is the absence of an `ITeamRotator` interface. In a production C# project, this would be expected for dependency injection and testability. However, for a challenge focused on simplicity, this is a reasonable trade-off.

### Testing Analysis

The 5 tests are high-quality: excellent naming convention (`Method_Scenario_ExpectedResult`), proper test isolation (constructor creates fresh instance for each test), and FluentAssertions for expressive expectations. The round-robin test verifies 4 sequential calls including the wrap-around. The inactive skip test verifies correct behavior with mixed active/inactive members.

The critical gap is quantity — only 5 tests for 5 behaviors leaves many scenarios untested. A competitive submission should have 15-20+ tests covering all edge cases. The absence of a single-active-member test, empty-team test, and boundary-input tests means the code's robustness is unverified in important scenarios.

### TeamRotator.cs — Complete Implementation (50 lines)

```csharp
namespace TeamRotator;

public class TeamRotator
{
    private readonly List<Member> _members = new();
    private int? _lastSelectedId;

    public void AddMember(int id, string name, bool isActive = true)
    {
        _members.Add(new Member(id, name, isActive));
    }

    public void SetManualLastSelected(int id)
    {
        _lastSelectedId = id;
    }

    public List<Member> GetNext(int count = 1)
    {
        var result = new List<Member>();
        for (var i = 0; i < count; i++)
        {
            var nextMember = FindNextValidMember();
            result.Add(nextMember);
            _lastSelectedId = nextMember.Id;
        }
        return result;
    }

    private Member FindNextValidMember()
    {
        var activeMembers = _members.Where(m => m.IsActive).ToList();
        if (!activeMembers.Any()) throw new InvalidOperationException("No active members available");
        if (activeMembers.Count == 1) return activeMembers.First();  // ✅ Single active → repetition allowed
        var lastIndex = _members.FindIndex(m => m.Id == _lastSelectedId);  // -1 if null → starts at 0
        for (var i = 1; i <= _members.Count; i++)
        {
            var currentIndex = (lastIndex + i) % _members.Count;
            var candidate = _members[currentIndex];
            if (candidate.IsActive && candidate.Id != _lastSelectedId) return candidate;  // ✅ Explicit no-repetition
        }
        return activeMembers.First();  // Fallback (should never reach)
    }
}
```
